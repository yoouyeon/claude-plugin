# devdocs 스펙

개발 산출물 문서를 한국어로 쓰고 검사하는 플러그인이다. 스킬은 두 개다.

- `write`: 문서를 문서 종류에 맞는 문체로 새로 쓰고, 다 쓴 뒤 정해진 항목을 검사한다.
- `review`: 이미 있는 문서를 같은 항목으로 검사해 보고하고, 사용자가 고른 항목만 고친다.

## 범위

다루는 문서는 다섯 종류다.

- 스펙·설계 문서
- 리서치 메모
- PR 본문
- 이슈 본문
- README

다루지 않는 것:

- 커밋 메시지. 형식이 프로젝트마다 정해져 있어서(Conventional Commits, 제목 길이 등) 범용 문체 규칙을 두지 않는다.
- 섹션 구성. 문서의 뼈대는 내용에 맞게 그때그때 정하고, 이 플러그인은 문장과 문체만 다룬다.
- 게시. 본문 작성까지만 한다. `gh pr create`, `gh issue create` 같은 게시는 하지 않는다.
- SKILL.md, 에이전트 파일. 모델이 읽는 지시문이라 사람이 읽는 문서와 기준이 다르다.

## write 스킬

### 발동

`/devdocs:write`로 부른다. description은 아래와 같다.

> 개발 산출물 문서를 한국어로 새로 쓸 때 쓰는 스킬. 스펙·설계 문서, 리서치 메모, PR 본문, 이슈 본문, README가 대상이다. "스펙 문서 써줘", "설계 문서 작성해줘", "PR 본문 써줘", "PR 설명 작성", "이슈 써줘", "조사한 거 메모로 정리해줘", "README 써줘" 같은 요청이 오면 실행한다. 이미 있는 문서를 고치는 요청과 커밋 메시지에는 쓰지 않는다.

### 동작

모호한 것은 추측하지 않고 사용자에게 묻는다. 문서 종류, 버전, 저장 위치가 모두 여기에 해당한다.

1. 요청에서 문서 종류를 정한다. 다섯 종류 중 하나로 정해지지 않으면 묻는다.
2. 버전을 정한다. 요청에 존댓말 지시가 없으면 기본 버전으로 쓴다.
3. 본문을 임시 파일에 쓴다. 다섯 종류 모두 같다. 위치는 작업 디렉토리 루트의 `.devdocs/<날짜시각>-<종류>.md`이고(예: `.devdocs/20261008-1530-pr.md`), 경로는 스크립트가 만든다. `.gitignore`는 만들지 않고, 임시 파일도 지우지 않는다. 필요 없으면 사용자가 지운다.
4. 1차 검사: 스크립트 검사와 모델 검사를 하고, 걸린 곳을 고친다.
5. 2차 검사: 스크립트 검사만 다시 한다. 고치면서 새로 생긴 문제를 잡는 단계다. 여기서 걸린 것은 더 고치지 않고 사용자에게 목록으로 보여 준다.
6. 결과를 전달한다.
   - PR·이슈 본문: 임시 파일 경로를 알려 준다. 사용자는 이 파일을 `gh pr create --body-file` 등에 쓴다.
   - 스펙, 리서치 메모, README: 저장할 위치를 묻고, 답한 위치로 옮긴다.

## review 스킬

### 발동

`/devdocs:review <파일>`로 부른다. description은 아래와 같다.

> 이미 있는 개발 산출물 문서를 검사하고, 사용자가 고른 항목만 고치는 스킬. 스펙·설계 문서, 리서치 메모, PR 본문, 이슈 본문, README가 대상이다. "이 문서 검사해줘", "README 리뷰해줘", "스펙 문체 확인해줘", "이 PR 본문 다듬어줘" 같은 요청이 오면 실행한다. 문서를 새로 쓰는 요청과 커밋 메시지에는 쓰지 않는다.

### 동작

모호한 것은 추측하지 않고 사용자에게 묻는다.

1. 대상 파일을 정한다. 요청에 파일이 없으면 묻는다.
2. 문서 종류와 버전을 정한다. 파일 위치와 내용으로 확실히 정해지지 않으면 묻는다.
3. 스크립트 검사와 모델 검사를 한다. 임시 파일은 만들지 않고 원본을 검사한다.
4. 걸린 곳을 줄 번호, 항목, 대안과 함께 목록으로 보여 주고 어느 항목을 고칠지 묻는다.
5. 사용자가 고른 항목만 원본 파일에서 고친다.
6. 스크립트 검사만 다시 한다. 여기서 걸린 것은 더 고치지 않고 사용자에게 목록으로 보여 준다.

## 문체

문서 종류마다 두 버전이 있다. 기본은 존댓말이 아닌 버전이고, 사용자가 요청하면 존댓말 버전으로 쓴다. 프로젝트 인원은 묻지 않는다.

| 문서 | 기본 | 존댓말 버전 |
|---|---|---|
| 스펙·설계 | -다체 | 합니다체 |
| 리서치 메모 | -다체 | 합니다체 |
| PR 본문 | 개조식 | 합니다체 |
| 이슈 본문 | 개조식 | 합니다체 |
| README | -다체 | 합니다체 |

개조식은 항목을 명사형이나 "-함"으로 짧게 끝내는 방식이다. 예: "인증 흐름 변경", "토큰 만료 시 재시도 추가함".

요청이나 스킬 인자에 "존댓말"이라는 말이 있으면 존댓말 버전으로 쓴다. 예: `/devdocs:write 존댓말 PR 본문`, "PR 본문 존댓말로 써줘". 사용자용 플래그는 따로 두지 않는다. 검사 스크립트에는 `--polite`를 넘긴다.

## 작성 지침

문서를 쓰는 동안 따르는 지침이다. 모두 "이렇게 쓴다"는 긍정형으로 적는다. 작성 단계에 금지 목록을 길게 넣으면 결과가 나빠진다는 실험 결과가 있어서, 금지 목록은 검사 단계에서만 쓴다(참고 사례 7).

1. 비유 대신 실제로 일어나는 동작과 결과를 쓴다.
2. 확인한 것, 추측한 것, 모르는 것을 구분해서 쓴다. 추측을 단정으로, 권고를 의무로 바꾸지 않는다.
3. 명사화하지 않고 동사로 쓴다. "검토를 진행한다"가 아니라 "검토한다".
4. 같은 대상은 같은 이름으로 부르고, 코드에 있는 대상은 코드의 실명을 쓴다. 기술 용어는 원어나 정착한 말을 쓰고 번역 명사를 새로 만들지 않는다.
5. 본문 문장은 서술어로 끝낸다. 제목, 목록, 표 칸은 명사형으로 끝나도 된다. 개조식 문서는 이 항목을 따르지 않는다.
6. 문서는 지금 상태를 설명한다. 변경 이력은 커밋 메시지와 PR 본문에 쓴다.
7. 문단으로 충분하면 불릿으로 쪼개지 않는다. 볼드는 놓치면 안 되는 곳에만 쓴다.
8. 줄표(—)로 정보를 잇지 않고, 문장을 나누거나 콜론을 쓴다.
9. 수치와 사례는 확인한 것만 쓴다.

## 검사

두 스킬이 같은 검사를 쓴다. 검사 순서와 횟수는 각 스킬의 "동작"을 따른다. 걸린 곳만 다시 보고, 걸렸다고 무조건 고치지 않는다. 이미 자연스러운 문장은 그대로 둔다.

스크립트가 세는 것과 허용치는 아래와 같다. 코드 블록과 인라인 코드 안은 모든 항목에서 세지 않는다.

| 항목 | 허용치 |
|---|---|
| 줄표(—, –) | 0 |
| 이모지 | 0 |
| 금지어 | 0 |
| 번역투 조사 표현 | 한 문단에 "~을 통해", "~에 대해", "~에 있어서"가 합쳐 3회 이상이면 걸림 |
| 종결어미 | 아래 표에 해당하면 걸림 |

종결어미는 버전마다 찾는 것이 다르다. 인용문(`>`)은 이 검사에서 뺀다.

| 문서 버전 | 찾는 것 |
|---|---|
| -다체 | "-니다.", "-요."로 끝나는 문장 |
| 합니다체 | "-니다"가 아닌 "-다."와 "-요."로 끝나는 문장 |
| 개조식 | "-니다.", "-요."로 끝나는 문장 |

금지어 표는 스킬 안에 내장하고 사용자별로 바꾸는 기능은 두지 않는다. 처음 넣을 항목은 아래와 같다.

| 표현 | 대신 |
|---|---|
| 박아 넣는다 | 그대로 적는다, 그대로 쓴다 |
| 고아(가 된다) | 실제 결과를 그대로. 예: "이전 데이터를 더 이상 찾지 못한다" |

모델이 판단하는 것:

- 상투적 마무리 문장
- 묻지 않은 후속 제안
- 근거 없는 평가어. 예: "매우 중요한", "혁신적인"
- "X가 아니라 Y" 대구의 반복
- 강조가 아닌 용도로 쓴 볼드. 예: 소제목 대신 쓴 볼드, 문장 전체를 감싼 볼드. 볼드가 적절한지는 개수로 정해지지 않아서 스크립트로 세지 않는다.
- 영어를 직역한 은유

## 참고 사례

2026-10-08에 조사한 커뮤니티 사례다. 번호는 작성 지침에서 인용할 때 쓴다.

1. [humanize-korean](https://github.com/epoko77-ai/im-not-ai): AI 티 패턴 70개 분류. 밀도 기준 판정, 과잉 교정 방지.
2. [korean-style-guard](https://github.com/basilro/korean-style-guard): 짧은 규칙 파일 + 저장 후 훅 검사.
3. [ko-ste](https://github.com/fivestar1103/ko-ste): 규칙 ID 체계. 직접 쓸 때와 남의 글을 고칠 때를 나눈다.
4. [lqez/korean-technical-writing](https://github.com/lqez/korean-technical-writing): 기술 문서 전용. 사실 보존을 1순위로 둔다.
5. [tech-doc-kr](https://github.com/Jeon0976/tech-doc-kr): 기술 문서 직역 은유 블랙리스트.
6. [humanizer-ko](https://github.com/IsaacEryn/humanizer-ko): 문서에 변경 이력을 서술하지 말라는 규칙(§30).
7. [korean-technical-writing-for-llms](https://github.com/JooyoungChoi14/korean-technical-writing-for-llms): 작성 단계에 금지 목록을 넣지 말라는 실험 결과.
